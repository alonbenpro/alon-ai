**Document ID:** INFRA-05
**Status:** Planned M8 operations gate; current foundation has safe logs and health endpoints but no telemetry backend, alert routes, on-call channels, production backups, incident tooling, or DR exercise
**Milestone:** M8 private operations and recurring readiness; M9 safety prerequisite
**Owner:** Solo operator wearing incident roles sequentially; provider/counsel specialists join only when incident facts require them
**Prerequisites:** OBS-01..05 exact registries/runbooks, TEST-01..06, INFRA-02..04, SEC-01..06, and a promoted private release

**Unlocks:** M8 private-operations acceptance and bounded M9 readiness review
**Risk:** Critical

## Outcome and timing

One operator is alerted through channels independent of Alon AI Gmail, can determine authoritative state, contain harm, restore a clean host/database/secrets/config, measure data loss and recovery time, and resume only by a separate gated command. Dashboards aid diagnosis but never replace PostgreSQL/provider/backup evidence.

## Current repository state

The API has liveness/readiness and sanitized structured logs; the worker emits `worker_ready`. The complete OBS-01 event schema, OBS-02 39-instrument/4,656-series registry and alerts, cost/evaluation telemetry, incident tables/catalog/IR-01..13, notification adapters, external heartbeats, backup metrics, recovery commands and drills remain planned. No on-call or disaster-recovery claim is currently supported.

## Scope and non-goals

In scope: local OpenTelemetry collector, managed encrypted logs/metrics/traces, DB-authoritative dashboards, telemetry self-health, exact OBS alert registry, incident tuple routing, primary/secondary external page channels, offline contacts, capacity/disk/cert/backup/release/provider/Gmail/security alerts, DR objectives/scenarios, clean rebuild/restore, exercises and evidence freshness. Non-goals: 24x7 staffed-SOC claim, Gmail as page channel, auto-remediation/auto-enable, high-cardinality identifiers, logs as product truth, undefined catch-all alerts, or hiding an outage because the monitoring vendor is down.

## Exact planned implementation surfaces

Create `infra/observability/otel-collector.yaml`, managed sink dashboards, `alert-routes.v1.json`, `heartbeat-jobs.v1.json`, `dr-objectives.v1.json`, local read-only diagnostic commands, offline encrypted contact sheet, and `scripts/dr/{preflight,rebuild,verify}.sh`. `alert-routes.v1.json` must equal OBS-02/OBS-05 alert IDs and exact `incident.catalog.v1` trigger/alert/runbook tuples; unknown/missing/cross-paired values fail deployment.

The host collector receives OTLP only on the internal network, applies OBS-01 allowlist/redaction/cardinality processors, buffers boundedly on encrypted local disk, exports over authenticated TLS to Google Cloud Monitoring, Logging and Trace, and emits its own drop/lag/queue/disk/clock health. Application metrics match the exact OBS-02 names/units/labels/buckets; Cloud Monitoring dashboards query authoritative read-only DB projections for controls, unresolved Gmail/cost/incidents and compare them to telemetry counts. No telemetry sink has an inbound control webhook.

Primary paging is PagerDuty mobile push/SMS/phone invoked by Cloud Monitoring alert policies. A healthy-host heartbeat is useful but is not Critical-alert delivery evidence. Every committed redacted Critical incident also atomically appends `CriticalSecondarySignalV1` to the PostgreSQL `outbox_messages` writer transaction; a database-unavailable Critical detected by the host appends the same record to a preallocated encrypted fsync spool before any acknowledgement. Its payload is exactly `{schema_version:"critical.secondary.signal.v1",status:"FAIL",severity:"CRITICAL",trigger_code,alert_code,runbook_code,occurred_minute_utc,occurrence_key}` where the three codes are closed catalog values, time is minute-bucketed and `occurrence_key` is an opaque random UUID used only for delivery dedupe. It contains no PII, secret, address, token, content, object path or dynamic metric label. A separate least-privilege sender posts directly—not through Cloud Monitoring, PagerDuty, the collector or application Gmail—to the secret URL for a dedicated Healthchecks.io **failure** endpoint. Durable dedupe is `(endpoint_generation,occurrence_key)`; attempts at 0/5/15/30 seconds, then every 60 seconds to 15 minutes, must deliver within 60 seconds for the gate, preserve the unsent record, and open local/offline escalation on breach. Provider `2xx` plus receipt hash commits delivery; timeout/unknown is retried idempotently and never authorizes business state.

A distinct daily synthetic Critical is the end-to-end primary watchdog. It injects a fixed canary through collector -> managed sink -> exact Cloud Monitoring policy -> PagerDuty -> human/signed test acknowledger. Only a verified PagerDuty event/ack receipt with matching canary generation and <=10-minute latency permits a success ping to a separate Healthchecks.io `critical-e2e-watchdog` endpoint. A host timer pings only its start endpoint, never success. Missing/mismatched/late stage leaves the watchdog red, emits the independent failure signal above, creates `TELEMETRY_OR_ALERT_BLINDNESS -> ALERT_TELEMETRY_BLINDNESS -> IR-11`, keeps both controls false after five minutes of send-safety blindness and invokes the offline phone/contact tree. PagerDuty delivery/ack and Healthchecks success are operational evidence only; neither updates product authority.

## Security, privacy, compliance, idempotency, observability, and cost

Collector/sinks/pages use scoped credentials, TLS, encryption, bounded retention and no inbound authority. Incident/page payloads expose only closed catalog values, minute bucket and opaque occurrence key; endpoint URLs are secrets and labels are static. Repeated alerts/incidents dedupe by canonical key without losing occurrences; delivery records and fsync spool are durable and idempotent. Notification success/failure never authorizes, resolves or mutates business state. The read-only AWS S3 witness probe exposes only fixed account/region/bucket, schema/key generation, sequence, exact object version/ETag/checksum, receipt hash, result and bounded age; it never logs object paths, tombstone targets or personal data. Its 100% fresh-authentication/zero-GCS-substitution SLO is a fail-closed readiness condition, not another business authority or a new telemetry instrument. External monitor/legal/support/restore/AWS account-recovery costs are budgeted and recorded; M8 real-provider acceptance plus counsel/transfer/processor/retention evidence explicitly accepts that loss of S3 authority can leave intact GCS data non-cutoverable. Counsel decides notification and communications; the system records references without privileged content. Exercise data is synthetic/minimized.

## Failure, rollback, and operator recovery

On missing/contradictory telemetry, page failure, breached objective, corrupt restore, provider/KMS uncertainty, route/config mismatch or unknown incident tuple: choose containment and unknown, set both controls false, disable public edge for any public/suppression/dependency uncertainty, use local read-only queries/offline journal, preserve evidence and execute the exact matrix runbook. For AWS S3 witness unavailability/ambiguity, return `30`, stop restore/cutover and new purge commitment, preserve GCS data/mirrors without treating them as commitment evidence, and recover the AWS account plus an independently held package through the signed custody procedure. For authenticated stale/forked/missing/invalid S3 lineage, return `40`, quarantine evidence and escalate IR-08/IR-13; GCS cannot reconstruct or vote on commitment. A deletion already committed by a proven conditional S3 `PutObject` remains mandatory apply while controls/services stay off. A failed `T7-AWS-WITNESS-ACCEPT` row blocks M8 pending an architecture amendment; no non-CAS fallback is allowed. Roll back collector/dashboard/alert/release configs by signed digest. Never resolve because a dashboard returned green, rewrite history, send a test to a real recipient, or auto-enable after recovery.
