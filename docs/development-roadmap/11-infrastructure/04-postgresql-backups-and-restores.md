## Outcome and timing

PostgreSQL product and `security_runtime` state can be recovered on a clean host to an exact target time without starting writers/providers, reviving sessions/controls, losing unresolved Gmail authority, or resurrecting purged data into use. Initial objective for an intact live provider is database RPO <=5 minutes and complete private-service RTO <=4 hours. A Google-wide outage has database RPO <=5 minutes only when the independently verified B2 WAL chain is current, isolated-data recovery RTO <=8 hours, and full-service RTO explicitly `N/A—not claimed` until alternate compute is separately vetted. Every value is proven by drills, never inferred from upload success.

PostgreSQL 18 documents continuous archiving and point-in-time recovery in the official [backup chapter](https://www.postgresql.org/docs/18/backup.html), accessed 2026-08-29. It is the database recovery contract; pgBackRest supplies the selected repository implementation below, and only a real isolated restore supplies gate evidence.

B2 Object Lock is enabled at bucket creation with governance retention, and the application key cannot delete locked versions. Exact bucket/account/endpoint IDs, default retention and a failed delete-before-retain-until test are signed. Two encrypted recovery packages held outside Google and the VPS contain read-only B2 credentials, `repo2` cipher pass, pinned pgBackRest binary/image digest, config hash and verification public keys; the B2 write key is not in the packages. Rotation writes a new package generation, verifies a full isolated repo-2 restore, then revokes the old credential. Loss, custody disagreement or simultaneous loss of repository and packages makes recovery unavailable (`30`), never green.

PostgreSQL uses `wal_level=replica`, `archive_mode=on`, `archive_timeout=300s`, and exact `archive_command='pgbackrest --stanza=alon-ai archive-push %p'`; pgBackRest must verify both repositories before returning success. Daily commands are `sudo -u postgres pgbackrest --stanza=alon-ai --repo=1 --type=full backup` and the same with `--repo=2`; hourly differentials are scheduled independently. `sudo -u postgres pgbackrest --stanza=alon-ai --repo=1 check`, `--repo=2 check`, and per-repository `info --output=json` must agree on stanza/system ID/timeline and required WAL coverage. A success in one repository never masks failure in the other: backup publication records `HEALTHY_BOTH`, `DIVERGENT`, or `UNAVAILABLE`; only `HEALTHY_BOTH` meets the dual-repository gate. Conflicting WAL, missing Object Lock, chain divergence or missed five-minute coverage sets controls false before spool exhaustion and opens IR-08. Primary-only recovery may continue for an ordinary B2 outage, but no purge may commit without both tombstone receipts and provider-outage readiness is stale until healed.

`BackupManifestV1` binds backup ID, repository number/provider/region/object versions and retention, cluster system identifier, PostgreSQL/pgBackRest exact versions and data checksum status, database/role/schema/Alembic/runtime versions, start/end/checkpoint/timeline/LSN/WAL range, file count/bytes/repository checksum, repository cipher/key generation IDs without values, release/config/46-table/retention-policy hashes, unresolved attempt/incident/control snapshot hash, command/artifact hashes and signature. A partial upload or repository disagreement is not a backup.

### Authoritative deletion-tombstone ledger

`RetentionCommandService` implements a fenced prepare-authorize-commit-apply protocol. `DeletionPreparedBundleV1` is evidence, never deletion authority. Its exact payload is `{schema_version:"retention.deletion_prepared_bundle.v1",command_id:uuid,idempotency_key:uuid,policy_manifest_hash:hex64,policy_version:string,prepared_at_utc:RFC3339,cutoff_utc:RFC3339,lookup_key_generation:string,target_snapshot_hash:hex64,entries:[{table_code:closed_enum,opaque_row_ref:base64url43,action:"DELETE"|"REDACT",record_generation:uint64}]}`. Entries are sorted by `(table_code,opaque_row_ref,action,record_generation)` and duplicates reject. `opaque_row_ref=base64url(HMAC-SHA-256(lookup_key_generation, RFC8785({table_code,primary_key_columns})))`; primary keys are read only inside retention/restore, never written externally, and canonical IDs may not be reused. `record_generation` is the signed 46-table retention-map row version, or literal `0` for a non-versioned never-reused primary key; no new product table/column or canonical domain state/event is introduced.

The PREPARED signature preimage is ASCII `alon-ai:retention-prepared:v1\n` followed by RFC 8785 payload bytes. `prepared_bundle_hash=hex(SHA-256(prepared_preimage))`; `signature=base64url(Ed25519-Sign(tombstone_signing_key_generation, decoded_prepared_bundle_hash))`. The encrypted objects are exactly `retention-ledger/v1/prepared/{command_id}.bin` in repo 1 and repo 2. After authenticated read/decrypt/exact-byte verification, each returns signed `DeletionPreparedReceiptV1={schema_version,command_id,prepared_bundle_hash,repository:"GCS_PRIMARY"|"B2_DR",bucket_account_id,object_version,retain_until_utc,verified_at_utc,verifier_key_generation}`. PREPARED has no sequence, previous committed hash or head field; it cannot advance a head and restore must never replay it. Payload/object names/metadata contain no PII, address, recipient hash, ciphertext field, raw personal data or provider value. Storage is client-side AES-256-GCM with separate repo wrapping generations as previously defined.

After both PREPARED receipts, one serializable PostgreSQL transaction reacquires the complete target graph, policy and holds and requires byte equality with `target_snapshot_hash`. It appends immutable internal audit record `DeletionAuthorizationV1={schema_version:"retention.deletion_authorization.v1",authorization_state:"AUTHORIZED_IRREVERSIBLE",authorization_id:uuid,command_scope,idempotency_key,command_id,prepared_bundle_hash,prepared_gcs_receipt_hash,prepared_b2_receipt_hash,policy_manifest_hash,policy_version,target_snapshot_hash,target_fence:[{table_code,primary_key_json,record_generation,action}],authorization_txid,authorized_at_utc}` while the existing `command_idempotency` row remains `IN_PROGRESS`. `target_fence` stays inside restricted PostgreSQL and never enters external objects/evidence. A post-commit strong read emits signed `DeletionAuthorizationProofV1={database_system_id,timeline,authorization_id,authorization_audit_event_id,authorization_payload_hash,authorization_txid,observed_wal_flush_lsn,observed_at_utc}` only after the audit row is visible and flushed.

Authorization is deliberately irreversible. The retention-owner role has no direct target-table DML; it can use only the registered purge procedure. A session-level advisory lock on literal key `alon-ai:retention-ledger:v1` serializes the ledger. Named database triggers generated from the 46-table retention manifest enforce one active authorized retention command, reject any target update/delete/version replacement, hold/policy substitution, cancellation, `FAILED` completion or second authorization after `AUTHORIZED_IRREVERSIBLE`, and allow mutation only to the same procedure carrying matching `authorization_id`, `authorization_txid`, target fence and later verified COMMITTED proof. Session death releases the advisory lock, but the next owner must recover the same authorization before starting another. Thus a target/policy change may invalidate PREPARED before authorization; after authorization it is structurally fenced and cannot invalidate or redirect the purge.

Only an authorized deletion can create `DeletionCommittedMarkerV1`. Its payload is `{schema_version:"retention.deletion_committed_marker.v1",sequence:uint64,previous_committed_marker_hash:hex64|"GENESIS",command_id,prepared_bundle_hash,prepared_gcs_receipt_hash,prepared_b2_receipt_hash,authorization_id,authorization_proof_hash,policy_manifest_hash,target_snapshot_hash,committed_at_utc}`. The COMMITTED preimage is ASCII `alon-ai:retention-committed:v1\n`, 32 decoded previous-marker bytes (zero bytes for genesis), then RFC 8785 payload bytes; `committed_marker_hash=hex(SHA-256(committed_preimage))` and Ed25519 signs its decoded hash. Objects are exactly `retention-ledger/v1/committed/{sequence-as-20-digits}.marker`. Both repositories must authenticate/read-verify the signed marker and produce `DeletionCommittedReceiptV1={schema_version,sequence,committed_marker_hash,repository,bucket_account_id,object_version,retain_until_utc,verified_at_utc,verifier_key_generation}`. Only then may compare-and-swap advance each signed head from the referenced prior head to `{schema_version:"retention.committed_head.v1",highest_contiguous_sequence,committed_marker_hash,gcs_committed_receipt_hash,b2_committed_receipt_hash,updated_at_utc}`. A head never references PREPARED directly.

The live purge procedure accepts only the exact authorized COMMITTED marker, both marker receipts and current head. It re-verifies marker/prepared/authorization/policy/target hashes, sequence and head, sets the transaction-local authorization fence, applies the complete delete/redact graph idempotently, appends immutable applied evidence, advances the database `committed_watermark`, and changes the existing command row to `SUCCEEDED` with result evidence in one transaction. Completion is acknowledged only after a post-commit strong read proves purge row absence/redaction hashes, applied audit evidence, command result and watermark. After COMMITTED, purge is mandatory: any application/DB failure leaves both controls false, keeps the authorization fenced, opens IR-13, and repair retries the same authorization/marker until APPLIED. `APPLIED` without a valid COMMITTED marker/head proof is impossible by role grants, procedure checks and deferred constraint triggers; direct/forged/missing-marker negatives must fail before the first target write.

The composite protocol states and only legal transitions are:

`NONE -> PREPARED_PARTIAL -> PREPARED_ONLY -> AUTHORIZED -> COMMITTING -> COMMITTED_PENDING_APPLY -> APPLIED_COMPLETED`; only `PREPARED_PARTIAL|PREPARED_ONLY -> QUARANTINED_PREPARED` may leave the main path. No transition returns from `AUTHORIZED`, changes its targets/policy or reaches APPLIED from any pre-COMMITTED state.

| State | Authoritative facts | Legal next step / recovery |
| --- | --- | --- |
| `NONE` | no prepared receipt, authorization, marker or applied evidence | create one bounded PREPARED attempt |
| `PREPARED_PARTIAL` | only one prepared object/receipt or interrupted verification | retry the same bytes to the missing repository or quarantine after proving no authorization/marker; never authorize/replay/head |
| `PREPARED_ONLY` | two verified prepared objects/receipts; no DB authorization | authorize exact unchanged snapshot or quarantine; never replay/head |
| `AUTHORIZED` | immutable DB authorization/proof and target/policy fences; no committed marker | controls false; create/verify COMMITTED for this authorization; cancel/alternate target/policy forbidden |
| `COMMITTING` | authorization plus partial marker upload/receipt or one-head CAS | no live apply; controls off; repair the same marker/head sequence and reject a new authorization |
| `COMMITTED_PENDING_APPLY` | contiguous signed marker plus both marker receipts/current external head; DB watermark not advanced | mandatory same-authorization live purge or restore replay |
| `APPLIED_COMPLETED` | live purge/applied evidence/command `SUCCEEDED`/database committed watermark in one transaction | post-commit acknowledgement; idempotent replay returns stored result |
| `QUARANTINED_PREPARED` | prepared-only object with signed proof that no authorization/marker exists | ignore forever for restore; after authoritative policy horizon and Object-Lock expiry, explicit-ID delete from both repos |

Crash fixtures are exact: P0 before PREPARED; P1 after one prepared upload; P2 after both prepared receipts/before authorization; P3 after authorization/before COMMITTED; P4 after one committed-marker upload; P5 after both marker receipts/before head CAS; P6 after one head CAS; P7 after matching contiguous COMMITTED heads/before purge; P8 after every purge write boundary; P9 after purge commit/before acknowledgement. P0-P2 never delete/replay and orphan PREPARED is quarantined only after both repositories plus PostgreSQL prove no authorization/marker. P3 is `AUTHORIZED`; P4-P6 are `COMMITTING`; all keep controls off and repair the same authorization/sequence. P7 is mandatory apply/replay. P8 rolls back all target/applied/watermark/result writes. P9 returns stored success. Concurrent prepare/authorize, stale authorization transaction fence, target/policy change before/after authorization, cancel, second authorization, forged receipt/marker/head and `APPLIED`-without-COMMITTED are focused negatives.

Restore authority is only the signed contiguous COMMITTED head and marker chain. Normal restore compares both heads; if one provider is unavailable, the surviving head is sufficient only when every post-watermark marker contains both valid prepared receipt hashes and authorization proof hash, is accompanied by both valid committed-marker receipts, and belongs to the contiguous head. Restore ignores/quarantines PREPARED_ONLY. A restored `AUTHORIZED` DB record without COMMITTED blocks cutover and repairs that same authorization into COMMITTED; it is not silently abandoned. Every COMMITTED marker after the restored `committed_watermark` is replayed in sequence, including COMMITTED-without-live-APPLIED, using the referenced prepared bundle to recompute row refs. `RestoreCutoverV1={restore_id,restored_committed_watermark,external_head_sequence,replayed_first_sequence,replayed_last_sequence,post_replay_row_absence_hash}` must equal a freshly reread surviving committed head before service start. Missing/forked prepared/authorization/marker/receipt/head proof, head advance during replay or any structural `APPLIED`-without-COMMITTED evidence leaves PostgreSQL paused, controls/public absent and all services off.

Retention starts with 14 daily and 4 weekly base-backup recovery chains in each repository, never exceeding 35 days unless a signed incident/legal hold requires it. WAL is retained until every recovery chain that depends on it and its hold has expired. Prune performs per-repository dry-run dependency graphs and object-version listings, signs candidates, requires explicit backup-set IDs, deletes only after a newer clean restore from that repository, and never prunes the deletion ledger before the authoritative retention/rights horizon plus every backup chain capable of predating it. Product row retention still follows DB-06/SEC-06 independently.

The upstream terminated-session duration conflict is not resolved here: SEC-02 describes minimized terminated session storage as `SAFETY_LONG`, while SEC-06 specifies terminated session detail 30 days. Backup/prune/restore code must read the authoritative signed `RetentionPolicyV1` at execution time, replay its tombstones before validation, and keep restored sessions revoked/expired. Until Task 6 reconciles the manifest, tests accept neither an infrastructure-hardcoded 30-day nor `SAFETY_LONG` duration.

Restore procedure:

1. `restore/preflight` resolves a new isolated host/network/empty target directory, target backup ID/time/LSN, selected repository, PostgreSQL system ID and zero provider credentials/routes/writers; it refuses a live mount, unresolved target or absent destructive confirmation. Repo-2 bootstrap starts from a clean non-Google host with the offline recovery package, verifies its custody signatures and pinned pgBackRest image before contacting B2.
2. For primary recovery run exact `pgbackrest --stanza=alon-ai --repo=1 --delta=n --type=time --target="$TARGET_UTC" --target-action=pause restore`; for off-provider recovery run the identical argv with literal `--repo=2`. The signed scenario may replace `--type=time --target="$TARGET_UTC"` only with literal `--type=lsn --target="$TARGET_LSN"` or `--type=immediate`; `PGDATA` remains the resolved empty target. Verify repository checksum/signature/object versions and required WAL before start.
3. Start PostgreSQL with network limited to the verifier role. At recovery pause/end, record timeline/LSN/time, restored `committed_watermark` and any `AUTHORIZED`-without-COMMITTED audit state; keep API, workers, SendGateway, Gmail credentials, public proxy and normal KMS/secret access absent.
4. Retrieve/authenticate both external committed heads. Ignore/quarantine prepared-only objects; repair an irreversible restored authorization to COMMITTED; replay only every verified contiguous COMMITTED marker after the restored committed watermark in sequence in isolated transactions. No application service starts if the committed chain/authorization proof cannot be established. Then revoke every restored session/flow, force both controls false and keep public profile absent.
5. Run `amcheck` where applicable; Alembic/catalog exact 46-table/FK/check/index/trigger/privilege equality; row/hash/event/audit/idempotency/outbox/workflow snapshot/incident/send-attempt-result-observation/cost/retention/tombstone checks; and recorded-fixture-only unresolved Gmail reconciliation with provider-call spy zero.
6. Only after signed verification may a new production host receive the database. Enabling workers, providers, controls or public ingress is separate and requires INFRA-05/incident gates. A Google-wide drill ends after independently decryptable isolated-data evidence; it does not claim full-service recovery.

Backup/restore command ownership is closed: archive/check/primary backup requirements map to `T7-BACKUP-PRIMARY`; repo-2/B2/Object-Lock/divergence requirements to `T7-BACKUP-DR`; prepared/authorized/committed/apply purge to destructive `T7-TOMBSTONE-PURGE`; primary restores to destructive `T7-RESTORE-PRIMARY`; and off-Google restores to destructive `T7-RESTORE-DR`. Exact invocations and exit semantics are in the [TEST-01 command registry](../10-testing/01-testing-strategy.md#closed-command-manifest). Destructive target manifests bind host/network/empty `PGDATA`, database/system ID, repository/object versions, target time/LSN, zero writers/credentials and confirmation digest. ## Security, privacy, compliance, idempotency, observability, and cost

Backups are pgBackRest client-side encrypted plus object-store protected, immutable/versioned, off-host and inaccessible to API/worker. Repository, tombstone lookup/signing and recovery keys are purpose-separated; two encrypted recovery packages remain outside Google/VPS. Tombstone payloads/object names/metadata contain no PII, address, recipient hash, ciphertext field or raw data. Manifests/logs contain safe hashes/IDs only. Upload/prune/restore use exact IDs and replay safely. Emit canonical backup/restore age/result metrics and alerts without object paths. B2 legal/transfer/terms/region/Object-Lock/storage/egress and restore-test cost evidence precedes provisioning or retention expansion. Holds/counsel decisions override pruning.

## Failure, rollback, and operator recovery

On archive gap, hash/signature/key/system-ID mismatch, missed RPO, failed verify/restore, full disk, unintended prune, tombstone failure or provider call: stop pruning/writers/workers as needed, set both controls false, preserve surviving backup/WAL/object versions and open IR-08/T10 incident. PREPARED without authorization is quarantined and never replayed; AUTHORIZED or COMMITTED cannot be cancelled/retargeted and IR-13 repair continues that exact authorization through mandatory apply. Restore only to a new isolated target and rotate/re-authorize lost secrets. Never alter a manifest, force recovery past corruption, delete WAL for space without dependency proof, or mount the failed target as production.
