## Outcome and timing

PostgreSQL product and `security_runtime` state can be recovered on a clean host to an exact target time without starting writers/providers, reviving sessions/controls, losing unresolved Gmail authority, or resurrecting purged data into use. Initial objective for an intact live provider is database RPO <=5 minutes and complete private-service RTO <=4 hours. A Google-wide outage has database RPO <=5 minutes only when the independently verified Amazon S3 repo-2 WAL chain is current, isolated-data recovery RTO <=8 hours, and full-service RTO explicitly `N/A—not claimed` until alternate compute is separately vetted. Every value is proven by drills, never inferred from upload success.

PostgreSQL 18 documents continuous archiving and point-in-time recovery in the official [backup chapter](https://www.postgresql.org/docs/18/backup.html), accessed 2026-08-29. It is the database recovery contract; pgBackRest supplies the selected repository implementation below, and only a real isolated restore supplies gate evidence.

Every retained-object upload supplies `Content-MD5` or an AWS SDK checksum as required by Object Lock, and evidence binds the request checksum, provider-returned checksum, ETag and version ID. Old non-PII authority-head and certificate versions remain retained. Exact account/bucket/region/endpoint, versioning/Object-Lock/policy/IAM hashes, default/minimum/maximum retention and failed delete/bypass/shorten/over-35-day backup tests are signed.

Rotation writes a new package generation, verifies a full isolated repo-2 restore and witness read, then revokes the old credential. Loss, custody disagreement or simultaneous loss of the AWS account and packages makes recovery unavailable (`30`), never green.

If AWS S3 fails any required documented or live-tested semantic, Task 7 does not weaken the CAS/Object-Lock contract and never falls back to the prior provider or non-CAS writes: a signed architecture amendment must select another provider with documented and live-tested CAS/Object Lock. No third provider is preselected.

PostgreSQL uses `wal_level=replica`, `archive_mode=on`, `archive_timeout=300s`, and exact `archive_command='pgbackrest --stanza=alon-ai archive-push %p'`; pgBackRest must verify both repositories before returning success. At signed Sunday 00:00 UTC the commands use `--type=full`; on the other six days they use `--type=diff`, independently for `--repo=1` and `--repo=2`. Continuous WAL supplies point-in-time coverage. Retention preserves exactly the newest 14 daily differential/full recovery points and the four weekly full base chains in each repository, with any overlap represented once in the catalog but counted in both asserted sets. `sudo -u postgres pgbackrest --stanza=alon-ai --repo=1 check`, `--repo=2 check`, and per-repository `info --output=json` must agree on stanza/system ID/timeline and required WAL coverage. A success in one repository never masks failure in the other: backup publication records `HEALTHY_BOTH`, `DIVERGENT`, or `UNAVAILABLE`; only `HEALTHY_BOTH` meets the dual-repository backup gate. A partial upload or repository disagreement is not a backup.

### Authoritative deletion-tombstone ledger

`RetentionCommandService` implements a fenced prepare-authorize-commit-apply protocol. `DeletionPreparedBundleV1` is evidence, never deletion authority. Its exact payload is `{schema_version:"retention.deletion_prepared_bundle.v1",command_id:uuid,idempotency_key:uuid,policy_manifest_hash:hex64,policy_version:string,prepared_at_utc:RFC3339,cutoff_utc:RFC3339,lookup_key_generation:string,target_snapshot_hash:hex64,entries:[{table_code:closed_enum,opaque_row_ref:base64url43,action:"DELETE"|"REDACT",record_generation:uint64}]}`. Entries are sorted by `(table_code,opaque_row_ref,action,record_generation)` and duplicates reject. `opaque_row_ref=base64url(HMAC-SHA-256(lookup_key_generation, RFC8785({table_code,primary_key_columns})))`; primary keys are read only inside retention/restore, never written externally, and canonical IDs may not be reused. `record_generation` is the signed 46-table retention-map row version, or literal `0` for a non-versioned never-reused primary key; no new product table/column or canonical domain state/event is introduced.

The PREPARED signature preimage is ASCII `alon-ai:retention-prepared:v1\n` followed by RFC 8785 payload bytes. `prepared_bundle_hash=hex(SHA-256(prepared_preimage))`; `signature=base64url(Ed25519-Sign(tombstone_signing_key_generation, decoded_prepared_bundle_hash))`. The encrypted objects are exactly `retention-ledger/v1/prepared/{command_id}.bin` in repo 1 and repo 2. After authenticated read/decrypt/exact-byte verification, each returns signed `DeletionPreparedReceiptV1={schema_version,command_id,prepared_bundle_hash,repository:"GCS_PRIMARY"|"AWS_S3_DR",bucket_account_id,object_version,object_etag,object_checksum,retain_until_utc,verified_at_utc,verifier_key_generation}`. PREPARED has no sequence, previous committed hash or head field; it cannot advance a head and restore must never replay it. Payload/object names/metadata contain no PII, address, recipient hash, ciphertext field, raw personal data or provider value. Storage is client-side AES-256-GCM with separate repo wrapping generations as previously defined.

After both PREPARED receipts, one serializable PostgreSQL transaction reacquires the complete target graph, policy and holds and requires byte equality with `target_snapshot_hash`. It appends immutable internal audit record `DeletionAuthorizationV1={schema_version:"retention.deletion_authorization.v1",authorization_state:"AUTHORIZED_IRREVERSIBLE",authorization_id:uuid,command_scope,idempotency_key,command_id,prepared_bundle_hash,prepared_gcs_receipt_hash,prepared_aws_s3_receipt_hash,policy_manifest_hash,policy_version,target_snapshot_hash,target_fence:[{table_code,primary_key_json,record_generation,action}],authorization_txid,authorized_at_utc}` while the existing `command_idempotency` row remains `IN_PROGRESS`. `target_fence` stays inside restricted PostgreSQL and never enters external objects/evidence. A post-commit strong read emits signed `DeletionAuthorizationProofV1={database_system_id,timeline,authorization_id,authorization_audit_event_id,authorization_payload_hash,authorization_txid,observed_wal_flush_lsn,observed_at_utc}` only after the audit row is visible and flushed.

Authorization is deliberately irreversible. The retention-owner role has no direct target-table DML; it can use only the registered purge procedure. A session-level advisory lock on literal key `alon-ai:retention-ledger:v1` serializes the ledger. Named database triggers generated from the 46-table retention manifest enforce one active authorized retention command, reject any target update/delete/version replacement, hold/policy substitution, cancellation, `FAILED` completion or second authorization after `AUTHORIZED_IRREVERSIBLE`, and allow mutation only to the same procedure carrying matching `authorization_id`, `authorization_txid`, target fence and later verified COMMITTED proof. Session death releases the advisory lock, but the next owner must recover the same authorization before starting another. Thus a target/policy change may invalidate PREPARED before authorization; after authorization it is structurally fenced and cannot invalidate or redirect the purge.

Amazon S3 is the **sole restore-authoritative commitment witness**. GCS holds a required verified pre-commit mirror and receipt but has no deletion head, no conditional-write authority and no fallback vote. Only an authorized deletion may create `DeletionCommitMarkerV1={schema_version:"retention.deletion_commit_marker.v1",sequence:uint64,previous_aws_s3_committed_certificate_hash:hex64|"GENESIS",command_id,prepared_bundle_hash,prepared_gcs_receipt_hash,prepared_aws_s3_receipt_hash,authorization_id,authorization_proof_hash,policy_manifest_hash,target_snapshot_hash,marker_created_at_utc}`. Its preimage is ASCII `alon-ai:retention-commit-marker:v1\n`, 32 decoded prior AWS S3 certificate-hash bytes (zero for genesis), then RFC 8785 payload bytes; `commit_marker_hash=hex(SHA-256(marker_preimage))` and Ed25519 signs the decoded hash.

Commit ordering is exact. First write the signed marker to GCS object `retention-ledger/v1/committed-mirrors/{sequence-as-20-digits}.marker`, then authenticate/read-verify exact bytes, retention and object generation and sign `GcsDeletionCommitMirrorReceiptV1={schema_version,sequence,commit_marker_hash,gcs_bucket_account_id,gcs_object_generation,retain_until_utc,verified_at_utc,verifier_key_generation}`. Only after that receipt exists may the service create `DeletionCommitCertificateV1={schema_version:"retention.deletion_commit_certificate.v1",witness:"AWS_S3_DR",sequence,previous_aws_s3_head_hash:hex64|"GENESIS",previous_aws_s3_head_object_version:string|"GENESIS",previous_aws_s3_head_etag:string|"GENESIS",previous_aws_s3_committed_certificate_hash:hex64|"GENESIS",commit_marker:DeletionCommitMarkerV1,commit_marker_hash,gcs_mirror_receipt:GcsDeletionCommitMirrorReceiptV1,gcs_mirror_receipt_hash,authorization_proof:DeletionAuthorizationProofV1,authorization_proof_hash,certificate_created_at_utc}`. The three embedded signed records make the required pre-commit GCS and database proof independently verifiable from Amazon S3 during a Google outage; their separately recomputed hashes must match the scalar hash fields. Certificate preimage is ASCII `alon-ai:retention-aws-s3-commit-certificate:v1\n`, 32 decoded prior AWS S3 head-hash bytes (zero for genesis), then RFC 8785 payload bytes; `commit_certificate_hash=hex(SHA-256(certificate_preimage))` and Ed25519 signs its decoded hash. Write it to the Object-Locked S3 object `retention-ledger/v1/committed/{sequence-as-20-digits}.certificate` with the required checksum, authenticate/read-verify the exact version ID, ETag, checksum, retention, envelope bytes and embedded signatures with the independent S3 read credential, and sign `AwsS3DeletionCommitCertificateReceiptV1={schema_version,sequence,commit_certificate_hash,aws_account_id,aws_s3_bucket,aws_s3_object_version,aws_s3_object_etag:string,aws_s3_checksum,retain_until_utc,verified_at_utc,verifier_key_generation}`.

The only commit point is the successful atomic conditional SigV4 `PutObject` of exact versioned object `retention-ledger/v1/authority/aws-s3-committed-head.json`. `AwsS3DeletionCommittedHeadV1={schema_version:"retention.aws_s3_deletion_committed_head.v1",witness:"AWS_S3_DR",highest_contiguous_sequence,commit_certificate_hash,commit_marker_hash,gcs_mirror_receipt_hash,aws_s3_certificate_object_version,aws_s3_certificate_object_etag:string,aws_s3_certificate_checksum,aws_s3_certificate_read_receipt_hash,previous_aws_s3_head_hash,previous_aws_s3_head_object_version:string|"GENESIS",previous_aws_s3_head_etag:string|"GENESIS",updated_at_utc}` is signed over ASCII `alon-ai:retention-aws-s3-committed-head:v1\n`, decoded previous AWS S3 head hash and its RFC 8785 payload. Genesis sends literal `If-None-Match: *`; every later write sends `If-Match: <current opaque ETag>`, while the signed payload independently binds the prior version ID, exact provider-returned ETag, hash and next sequence from one fresh authenticated read. The request includes `Content-MD5` or a supported SDK checksum and never uses copy/multipart.

No HTTP status alone authorizes live apply. After every `200`, `409`, `412` or timeout/lost response, the verifier performs a strong read of the current head and then an exact `versionId` read, binding exact bytes, signature, head hash, opaque ETag, checksum and referenced certificate. Exact new head/certificate proves COMMITTED; exact old head proves not committed and permits only a freshly conditioned retry of the same authorization; a different next certificate, mismatched `200` response version/ETag/checksum, fork, gap or invalid signature is exit `40`; unavailable or ambiguous read is exit `30`. The verifier signs `AwsS3DeletionHeadConditionalWriteReceiptV1={schema_version:"retention.aws_s3_deletion_head_conditional_write_receipt.v1",sequence,request_id,http_result:"200"|"409"|"412"|"TIMEOUT",condition_kind:"IF_NONE_MATCH"|"IF_MATCH",prior_head_hash,prior_head_object_version,prior_head_etag:string,new_head_hash,new_head_object_version,new_head_etag:string,new_head_checksum,commit_certificate_hash,result:"COMMITTED"|"NOT_COMMITTED",verified_at_utc,verifier_key_generation}`. A committed receipt is mandatory before live apply. GCS remains only the pre-commit marker mirror and never receives or votes on the authority head.

The live purge procedure accepts only the exact authorized commit marker/certificate, required GCS mirror receipt, AWS S3 certificate receipt and authenticated authoritative S3 head/conditional-write evidence. It re-verifies marker/prepared/authorization/policy/target hashes, AWS S3 sequence/head and receipt chain, sets the transaction-local authorization fence, applies the complete delete/redact graph idempotently, appends immutable applied evidence, advances the database `committed_watermark`, and changes the existing command row to `SUCCEEDED` with result evidence in one transaction. Completion is acknowledged only after a post-commit strong read proves purge row absence/redaction hashes, applied audit evidence, command result and watermark. After AWS S3 COMMITTED, purge is mandatory and GCS has no post-commit role: any application/DB failure leaves both controls false, keeps the authorization fenced, opens IR-13, and repair retries the same authorization/certificate until APPLIED. `APPLIED` without valid AWS S3 authoritative head/certificate/conditional-write proof is impossible by role grants, procedure checks and deferred constraint triggers; direct/forged/missing-witness negatives fail before the first target write.

The composite protocol states and only legal transitions are:

`NONE -> PREPARED_PARTIAL -> PREPARED_ONLY -> AUTHORIZED -> COMMITTING -> COMMITTED_PENDING_APPLY -> APPLIED_COMPLETED`; only `PREPARED_PARTIAL|PREPARED_ONLY -> QUARANTINED_PREPARED` may leave the main path. No transition returns from `AUTHORIZED`, changes its targets/policy or reaches APPLIED from any pre-COMMITTED state.

| State | Authoritative facts | Legal next step / recovery |
| --- | --- | --- |
| `NONE` | no prepared receipt, authorization, marker or applied evidence | create one bounded PREPARED attempt |
| `PREPARED_PARTIAL` | only one prepared object/receipt or interrupted verification | retry the same bytes to the missing repository or quarantine after proving no authorization/marker; never authorize/replay/head |
| `PREPARED_ONLY` | two verified prepared objects/receipts; no DB authorization | authorize exact unchanged snapshot or quarantine; never replay/head |
| `AUTHORIZED` | immutable DB authorization/proof and target/policy fences; no committed marker | controls false; create/verify COMMITTED for this authorization; cancel/alternate target/policy forbidden |
| `COMMITTING` | authorization plus incomplete GCS mirror/receipt, AWS S3 certificate/read, pre-conditional-write state, or unresolved S3 response | no live apply without reconciled AWS S3 authority; controls off; repair the same sequence and reject a new authorization |
| `COMMITTED_PENDING_APPLY` | successful/read-reconciled AWS S3 conditional head write names the certificate/marker; DB watermark not advanced | mandatory same-authorization live purge or restore replay; GCS has no post-commit role |
| `APPLIED_COMPLETED` | live purge/applied evidence/command `SUCCEEDED`/database committed watermark in one transaction | post-commit acknowledgement; idempotent replay returns stored result |
| `QUARANTINED_PREPARED` | prepared-only object with signed proof that no authorization/marker exists | ignore forever for restore; after authoritative policy horizon and Object-Lock expiry, explicit-ID delete from both repos |

Crash fixtures are exact: P0 before PREPARED; P1 after one prepared upload; P2 after both prepared receipts/before authorization; P3 after authorization/before GCS mirror; P4 after verified GCS marker mirror/receipt; P5 after authenticated AWS S3 certificate read/before head write; P6 after the conditional `PutObject` request with `200|409|412|timeout` requiring exact read reconciliation; P7 after a successful or read-reconciled AWS S3 head write/before purge; P8 after every purge write boundary; P9 after purge commit/before acknowledgement. P0-P2 never delete/replay and orphan PREPARED is quarantined only after both repositories plus PostgreSQL prove no authorization/certificate. P3-P5 are `AUTHORIZED|COMMITTING` and are not externally committed. At P6 an authenticated strong AWS S3 current/exact-version read alone decides: the exact new certificate is COMMITTED, the exact old head is not, unavailable/ambiguous is exit `30`, and any different/mismatched lineage is exit `40`; GCS is not consulted. P7 is mandatory apply/replay. P8 rolls back all target/applied/watermark/result writes. P9 returns stored success. Concurrent prepare/authorize, stale authorization/ETag fence, target/policy change, cancel, second authorization, missing GCS pre-commit receipt, forged/forked/stale/missing AWS S3 certificate/head, unconditional writes and `APPLIED`-without-AWS-S3-COMMITTED are focused negatives.

Restore authority is only the signed contiguous AWS S3 COMMITTED head/certificate chain. Every normal, GCS-data, AWS-S3-data, Google-wide-outage and isolated drill restore must authenticate the independent recovery package, S3 head exact version ID/ETag/checksum, conditional-write lineage, certificates, their embedded GCS mirror receipts and authorization proofs, and the referenced S3 prepared objects before replay/cutover. Live GCS access is unnecessary for authority verification during a Google outage because the signed S3 certificate embeds the already verified GCS receipt and marker; GCS still has no vote. Backup base/WAL data may come from either verified pgBackRest repository, but deletion replay authority always comes from Amazon S3. Restore ignores/quarantines PREPARED_ONLY. A restored `AUTHORIZED` DB record without AWS S3 COMMITTED blocks cutover and waits/repairs the same authorization; it is not silently abandoned. Every S3-committed certificate after the restored `committed_watermark` is replayed in sequence, including COMMITTED-without-live-APPLIED, using the referenced prepared bundle to recompute row refs. `RestoreCutoverV1={restore_id,restored_committed_watermark,aws_s3_authority_head_sequence,aws_s3_authority_head_hash,aws_s3_authority_head_object_version,aws_s3_authority_head_etag,aws_s3_authority_head_checksum,replayed_first_sequence,replayed_last_sequence,post_replay_row_absence_hash}` must equal a freshly authenticated AWS S3 head immediately before service start.

| Available recovery components | Backup data source | Deletion authority and result |
| --- | --- | --- |
| GCS + AWS S3 healthy | either verified repo | authenticate AWS S3 head/certificates; replay/cutover allowed if all checks pass |
| GCS backup data only, AWS S3 authority reachable | GCS repo 1 | AWS S3 still decides deletion commitment; GCS data restore may proceed |
| AWS S3 backup data/authority only, Google unavailable | AWS S3 repo 2 | AWS S3 decides and supplies data; Google-wide isolated recovery may proceed |
| GCS available, AWS S3 backup data unavailable but authority objects reachable | GCS repo 1 | AWS S3 authority read remains mandatory; proceed only with the complete certificate chain |
| AWS S3 service, authority head, or independent recovery package unavailable/ambiguous | either/none | exit `30` not-pass; no restore/cutover/new commitment; services/public/controls off; GCS cannot substitute |
| authenticated AWS S3 head/certificate is stale, forked, missing a sequence/receipt, or signature/hash/conditional-write lineage fails | either repo | exit `40` integrity failure; quarantine evidence, IR-08/13; no GCS fallback |

This is an explicit availability tradeoff: loss of AWS S3 authority can make otherwise intact GCS backup data non-cutoverable until AWS account/package recovery. That sacrifice is required for one deterministic privacy-deletion truth. S3 Object Lock/versioning preserves the authoritative head, certificates/receipts and referenced prepared objects for the approved rights/legal horizon only because those schemas are independently proven non-PII; backup/WAL/object versions containing recoverable personal data still expire by 35 days and cannot be hidden by runtime delete markers. M8 provider acceptance and legal/transfer/processor/region/account-recovery/cost evidence must accept this sole-witness dependency; GCS retention cannot shorten or waive it. Missing/forked prepared/authorization/GCS-mirror/S3-certificate/head proof, head advance during replay or any structural `APPLIED`-without-AWS-S3-COMMITTED evidence leaves PostgreSQL paused, controls/public absent and all services off.

Canonical `OPERATIONAL_BACKUP_CHAINS` is exactly 14 daily recovery points plus four weekly full chains per repository. WAL is retained only through every live dependency and always pruned so no personal-data point older than 35 days is recoverable. Legal, incident, rights, disaster, or operator holds never extend a general backup, WAL segment, Object-Lock version, or PITR point; the owner must extract/minimize needed evidence into governed live/restricted storage before expiry. Prune performs per-repository dry-run dependency graphs and object-version listings, signs candidates, requires explicit backup-set IDs, and refuses a policy configuration whose dependency/lock date would cross 35 days. The non-PII deletion ledger follows its separate witness horizon. Product row retention still follows DB-06/SEC-06 independently.

Canonical `AUTH_RUNTIME_DETAIL` resolves session retention: operational terminated-session detail is purged no later than 30 days after termination; only separately minimized auth audit is `SAFETY_LONG`. Backup/prune/restore reads the signed policy, replays tombstones before validation, and keeps restored sessions revoked/expired. No infrastructure override or hold may preserve session-detail recovery past its policy/35-day backup ceiling.

Restore procedure:

1. `restore/preflight` resolves a new isolated host/network/empty target directory, target backup ID/time/LSN, selected repository, PostgreSQL system ID and zero provider credentials/routes/writers; it refuses a live mount, unresolved target or absent destructive confirmation. Every restore, including one whose base/WAL data comes from repo 1, loads an independently held AWS S3 recovery package, verifies its custody signatures, account/region/bucket identity, verifier generations and pinned tooling, then performs a fresh authenticated current/exact-version read of the S3 authority head before touching the target. Repo-2 bootstrap additionally starts from a clean non-Google host and verifies the pinned pgBackRest image before contacting Amazon S3.
2. For primary recovery run exact `pgbackrest --stanza=alon-ai --repo=1 --delta=n --type=time --target="$TARGET_UTC" --target-action=pause restore`; for off-provider recovery run the identical argv with literal `--repo=2`. The signed scenario may replace `--type=time --target="$TARGET_UTC"` only with literal `--type=lsn --target="$TARGET_LSN"` or `--type=immediate`; `PGDATA` remains the resolved empty target. Verify repository checksum/signature/object versions and required WAL before start.
3. Start PostgreSQL with network limited to the verifier role. At recovery pause/end, record timeline/LSN/time, restored `committed_watermark` and any `AUTHORIZED`-without-COMMITTED audit state; keep API, workers, SendGateway, Gmail credentials, public proxy and normal KMS/secret access absent.
4. Retrieve and authenticate the sole AWS S3 authority head, its exact version ID/ETag/checksum, signed conditional-write lineage and the contiguous certificate chain it names; authenticate each referenced GCS mirror receipt as supporting evidence, never as a head or substitute authority. Ignore/quarantine prepared-only objects; repair an irreversible restored authorization to COMMITTED only through the same S3 conditional `PutObject` protocol; replay only every verified contiguous AWS-S3-COMMITTED certificate after the restored committed watermark in sequence in isolated transactions. Missing, stale, forked, unavailable or ambiguous S3 authority is exit `30` for unavailable/ambiguous access or `40` for authenticated integrity failure: the target remains isolated and no service starts. Then revoke every restored session/flow, force both controls false and keep public profile absent.
5. Run `amcheck` where applicable; Alembic/catalog exact 46-table/FK/check/index/trigger/privilege equality; row/hash/event/audit/idempotency/outbox/workflow snapshot/incident/send-attempt-result-observation/cost/retention/tombstone checks; and recorded-fixture-only unresolved Gmail reconciliation with provider-call spy zero.
6. Only after signed verification may a new production host receive the database. Enabling workers, providers, controls or public ingress is separate and requires INFRA-05/incident gates. A Google-wide drill ends after independently decryptable isolated-data evidence; it does not claim full-service recovery.

Backup/restore command ownership is closed: archive/check/scheduled backups for both repositories map to `T7-BACKUP-BOTH`; the one real preselection AWS semantic gate maps to destructive `T7-AWS-WITNESS-ACCEPT`; prepared/authorized/committed/apply purge maps to destructive `T7-TOMBSTONE-PURGE`; primary restores map to destructive `T7-RESTORE-PRIMARY`; and off-Google restores map to destructive `T7-RESTORE-DR`. Exact invocations and exit semantics are in the [TEST-01 command registry](../10-testing/01-testing-strategy.md#closed-command-manifest). Destructive target manifests bind host/network/empty `PGDATA`, database/system ID, account/region/repository/object versions, target time/LSN, zero writers/credentials and confirmation digest. Unavailable=`30`, integrity/chain=`40`, unsafe target=`50`, partial external receipt=`60`; none passes.

## Security, privacy, compliance, idempotency, observability, and cost

Backups are pgBackRest client-side encrypted plus object-store protected, immutable/versioned, off-host and inaccessible to API/worker. Repository, tombstone lookup/signing and recovery keys are purpose-separated; two encrypted recovery packages remain outside Google/VPS. Tombstone payloads/object names/metadata contain no PII, address, recipient hash, ciphertext field or raw data. Manifests/logs contain safe hashes/IDs only. Upload/prune/restore use exact IDs and replay safely. Emit canonical backup/restore age/result metrics and alerts without object paths. The AWS S3 witness readiness SLO is 100% of new deletion commitments and restore/cutover attempts authenticated against a fresh exact-version S3 head, with zero GCS substitutions: probe the head/certificate chain read-only every five minutes, expire readiness after 15 minutes, and always repeat the synchronous read at commit, restore preflight and immediately before cutover. One unavailable/ambiguous probe makes witness readiness false and raises `ALERT_BACKUP_RESTORE`; a pending restore or irreversible authorization additionally keeps services/public/controls off. This reuses canonical backup/restore telemetry and adds no instrument to the exact 39-instrument registry. Real-provider M8 acceptance plus AWS legal/transfer/terms/region/Object-Lock/storage/egress, sole-witness availability, account recovery and restore-test cost evidence precedes production provisioning or retention expansion. Legal/incident/counsel hold precedence applies only to eligible live product/restricted records under DB-06/SEC-06; it never extends auth-flow/session detail, token/key maximums, or any backup/WAL/Object-Lock/PITR point capable of recovering personal data past the signed 35-day ceiling. Required held evidence is extracted and minimized before those hard expiries.

## Failure, rollback, and operator recovery

On archive gap, hash/signature/key/system-ID mismatch, missed RPO, failed verify/restore, full disk, unintended prune, tombstone failure or provider call: stop pruning/writers/workers as needed, set both controls false, preserve surviving backup/WAL/object versions and open IR-08/T10 incident. PREPARED without authorization is quarantined and never replayed; AUTHORIZED before the AWS S3 conditional head write remains fenced and not externally committed, while a successful or exact-read-reconciled conditional write is irrevocably COMMITTED and IR-13 repair continues that exact authorization through mandatory apply; GCS has no post-commit role. If Amazon S3 or its independent recovery package is unavailable/ambiguous, return `30`, stop new deletion commitment and restore/cutover, keep all service/public/control paths off, preserve the GCS mirror without treating it as authority, and recover AWS account/package access through the signed custody runbook. An authenticated stale/forked/missing/invalid S3 chain returns `40`, quarantines all evidence and escalates IR-08/IR-13; no operator override or GCS reconstruction can manufacture commitment state. A failed M8 acceptance row additionally requires an architecture amendment before production provisioning. Restore only to a new isolated target and rotate/re-authorize lost secrets. Never alter a manifest, force recovery past corruption, delete WAL for space without dependency proof, or mount the failed target as production.
