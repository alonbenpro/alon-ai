### Canonical input/result digest contract

`workflow_runs.input_hash/result_hash`, `command_idempotency.request_hash/result_hash`, and `evaluation_cases.input_hash/expected_hash` use one byte-level algorithm: lowercase hexadecimal SHA-256 over the UTF-8 bytes of RFC 8785 canonical JSON for the exact envelope `{"schema_version":<string>,"payload":<json>}`. The stored `*_schema_version` string is copied byte-for-byte into `schema_version`; the stored JSONB snapshot is the `payload`. Producers reject duplicate object keys, non-I-JSON numbers, invalid Unicode, NaN, and infinities before canonicalization. Hashing PostgreSQL's textual JSON/JSONB rendering, pretty JSON, a payload without the envelope, or an integer schema version is invalid.

Input schema version/snapshot/hash are always non-NULL. A workflow result is absent only when all three result columns are SQL `NULL`; only `SUCCEEDED` may carry a result. JSON `null` is a present payload, not an absent result, and therefore has a schema version and digest. A reader first validates the lowercase digest against the stored version/payload bytes, then dispatches the validator registered for that exact version. Upcasters may transform a verified snapshot in memory, but never rewrite or rehash the stored row; an incompatible input starts a new workflow run, and an incompatible result requires a new consumer/version.

Normative UTF-8 fixture vectors (the canonical byte string shown has no trailing LF) are:

| Schema/payload | RFC 8785 canonical envelope bytes | SHA-256 |
| --- | --- | --- |
| `workflow.input.v1` / `{"a":1,"b":"é","nested":[true,null]}` | `{"payload":{"a":1,"b":"é","nested":[true,null]},"schema_version":"workflow.input.v1"}` | `cdd6c7c8b49d6cd13cb6ff576332a6025726b9dc784adb9fb7b15a6da69891a0` |
| `workflow.result.v1` / `{"count":0,"ok":true}` | `{"payload":{"count":0,"ok":true},"schema_version":"workflow.result.v1"}` | `22b3184b0e4a82b832b3cc99e2079073f4fb9b900be0c7a744b0fd9ae2755e12` |
| `command.request.v1` / `{}` | `{"payload":{},"schema_version":"command.request.v1"}` | `d6f79e906be21e0a9a0ea9f4cec513bacb1b27126d7e4b91ab99d9e39f9bbbb3` |

Migration and fixture acceptance require two independent RFC 8785 implementations to reproduce all three vectors and reject altered schema-version type, key order assumptions, extra whitespace, Unicode escaping differences, and absent-versus-JSON-null confusion.

The M2 unit of work locks or version-checks one aggregate and atomically writes its row, domain event, audit event, command idempotency result, and outbox record. External calls never occur inside that transaction. `workflow_runs` is an application projection: DBOS or Temporal system tables are runtime-owned and never joined as business truth. The incident trigger/runbook/alert/resolution sets are the closed `incident.catalog.v1`: unknown version/value, a cross-paired trigger/alert/runbook tuple, or an inapplicable resolution aborts before insert. `MITIGATED_NO_LOSS` and `FALSE_POSITIVE_VERIFIED` apply to every trigger; all other applicability is the exact `ck_incidents_resolution_applicability` mapping. Residual-risk acceptance is additionally limited to INFO/LOW/MEDIUM and the eight explicitly listed waivable triggers; credential, privacy, suppression, send, Gmail ambiguity, restore, Google-policy/legal-review and recipient-hash-enumeration routes cannot be waived. A catalog change uses an additive migration plus application dual-read/old-write drain, explicit v2 promotion, and retained v1 reader; stored rows are never relabeled in place.

### Stable workflow identity

Every product run uses application UUID `workflow_run_id` and runtime ID `experiment:{experiment_id}:{workflow_type}:v{workflow_version}:run:{workflow_run_id}`. Retrying a failed experiment stage creates a new `workflow_run_id`; replaying a command returns the existing run. Runtime migration preserves the application UUID/correlation chain while creating a new runtime identity only through an audited handoff.

## Security, privacy, compliance, idempotency, observability, and cost

The single operator still receives explicit row ownership; future tenancy is not implied. No credential, message body, or unnecessary personal data belongs in core tables. Every command has a scoped idempotency key. Logs expose safe IDs, state, versions, duration, and reason codes. Budget reserve/reconcile uses original provider currency and a separately recorded ILS reporting conversion; it never silently converts stored amounts.

## Failure, rollback, and operator recovery

Migration failure rolls back and leaves outreach disabled. A bad application release is rolled back before an audited repair command; direct production row edits are forbidden. Unknown runtime mapping, impossible state, version gap, overspend, or missing gate evidence opens an incident and blocks mutation. Restore uses the M2 backup/restore procedure in DB-06 and verifies constraints before worker start.
