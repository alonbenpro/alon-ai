## Outcome and timing

M2 creates the first product system of record. It starts only after M1 accepts DBOS or the mandatory Temporal handoff is complete. M1's `m1_spike` schema is disposable evidence infrastructure and must never be migrated, copied, or renamed into these tables.

All product identifiers are UUIDs generated by an injected `IdGenerator`; instants are UTC `timestamptz`; money is integer minor units plus ISO-4217 currency; mutable aggregates carry `version bigint not null check (version > 0)`. PostgreSQL constraints reject impossible stored facts even when application validation is bypassed.

## Scope and non-goals

In scope: one-operator ownership, experiment aggregate roots, application workflow projections, fail-closed controls, budget accounting, incident tracking, exact keys, constraints, indexes, transaction ownership, and deletion/retention class references.

Non-goals: multi-tenancy, organizations/RBAC, billing, event sourcing as the read model, engine-native history as product truth, generic entity/attribute tables, soft foreign keys, Kafka, or importing M1 spike records.

The M2 unit of work locks or version-checks one aggregate and atomically writes its row, domain event, audit event, command idempotency result, and outbox record. External calls never occur inside that transaction. `workflow_runs` is an application projection: DBOS or Temporal system tables are runtime-owned and never joined as business truth.

After DB-02 creates `experiment_briefs`, add a deferrable composite foreign key from `experiments(experiment_id,active_brief_version)` to `experiment_briefs(experiment_id,brief_version)`. After DB-05 creates `cost_entries`, add the declared `budget_reservations.cost_entry_id` foreign key. Both are installed in DB-06's deferred cross-domain-FK revision and verified by name.

### Stable workflow identity

Every product run uses application UUID `workflow_run_id` and runtime ID `experiment:{experiment_id}:{workflow_type}:v{workflow_version}:run:{workflow_run_id}`. Retrying a failed experiment stage creates a new `workflow_run_id`; replaying a command returns the existing run. Runtime migration preserves the application UUID/correlation chain while creating a new runtime identity only through an audited handoff.

## Test strategy

- **Unit `test_experiment_failure_fields_match_state`:** every invalid state/field combination is rejected.
- **Migration `test_schema_has_all_named_constraints_and_indexes`:** introspect PostgreSQL by exact name.
- **Integration `test_state_event_audit_idempotency_outbox_are_atomic`:** inject failure after every write.
- **Concurrency `test_budget_reservation_cannot_exceed_account`:** serialize/lock the account and deny overspend.
- **Recovery `test_workflow_projection_rebuild_does_not_mutate_aggregate`:** runtime recovery never becomes business authority.
- **Security `test_disabled_operator_cannot_change_control`:** auth and audit denial are retained.

## Security, privacy, compliance, idempotency, observability, and cost

The single operator still receives explicit row ownership; future tenancy is not implied. No credential, message body, or unnecessary personal data belongs in core tables. Every command has a scoped idempotency key. Logs expose safe IDs, state, versions, duration, and reason codes. Budget reserve/reconcile uses original provider currency and a separately recorded ILS reporting conversion; it never silently converts stored amounts.

## Failure, rollback, and operator recovery

Migration failure rolls back and leaves outreach disabled. A bad application release is rolled back before an audited repair command; direct production row edits are forbidden. Unknown runtime mapping, impossible state, version gap, overspend, or missing gate evidence opens an incident and blocks mutation. Restore uses the M2 backup/restore procedure in DB-06 and verifies constraints before worker start.
